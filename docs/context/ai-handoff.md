## 1. What is KASIRSOLO?

KASIRSOLO is an Indonesian SaaS platform that provides Point of Sale (POS) applications for small businesses. It is a **multi-tenant, multi-app platform** where each client (business) subscribes to one or more kasir (cashier) applications.

**Target market**: Small businesses in Solo/Surakarta, Indonesia — warung makan, toko kelontong, laundry, bengkel, salon, etc.

**Business model**: 14-day free trial, then monthly subscription per app. Priced in IDR.

## 4. Auth Strategy

KASIRSOLO uses a **dual auth strategy**:

### Admin Dashboard
- Supabase Auth with email + password
- JWT tokens managed by Supabase client
- Middleware checks auth state

### All Kasir Apps (kasir-fnb, kasir-toko, kasir-laundry, etc.)
- **WhatsApp number + 6-digit PIN** (custom implementation, NOT Supabase Auth)
- WhatsApp number is the login identifier
- PIN is a 6-digit numeric code (hashed in database)
- Quick PIN switch for multi-user shared devices
- Session cached in IndexedDB for offline support
- PIN reset via WhatsApp message

### Why WhatsApp + PIN?
- Indonesian users are WhatsApp-first (99%+ penetration)
- Faster than email-based auth for the target demographic
- Enables quick user switching on shared POS devices
- Registration credentials sent via WhatsApp (no email verification needed)

See `docs/flows/auth-flow.md` for full flow diagrams.

## 5. Multi-Tenant Architecture

```
ksp_clients (business entity)
  └── ksp_licenses (per-app subscription)
       ├── ksp_users (staff accounts — WhatsApp + PIN auth)
       ├── ksp_devices (registered devices)
       └── [app data] (products, sales, etc.)
```

- `license_id` is the primary isolation key
- ALL app data tables MUST have `license_id`
- RLS policies enforce data isolation at the DB level

## 7. Database Conventions

- All platform tables prefixed with `ksp_` (KasirSolo Platform)
- All app tables prefixed with app abbreviation (e.g., `fnb_`, `toko_`, `laundry_`)
- Every app data table has `license_id` (UUID, FK to ksp_licenses)
- Timestamps: `created_at`, `updated_at` (with triggers)
- Soft delete: `is_active` boolean or `deleted_at` timestamp
- IDs: UUID (generated by Supabase)
- `ksp_users` uses `whatsapp` + `pin` for authentication (NOT email/password via Supabase Auth)
- `ksp_users.whatsapp` is unique per license (UNIQUE constraint on `whatsapp + license_id`)
- `ksp_users.pin` is unique per license (for quick-switch functionality)
- `ksp_users.email` and `ksp_users.auth_user_id` are nullable (not used for kasir app auth)

## 8. Key Business Rules

1. **Trial**: 14 days, full access, no payment required
2. **License lifecycle**: trial → active → expired → suspended
3. **Device limits**: Based on plan (1/3/5 devices per license)
4. **Roles**: owner (full), manager (operational), cashier (POS only)
5. **Auth**: WhatsApp + PIN for all kasir apps; email + password for admin only
6. **PIN uniqueness**: PIN must be unique within a license (enables quick-switch)
7. **WhatsApp uniqueness**: WhatsApp number unique per license for users, unique globally for clients
8. **Offline**: POS works offline (IndexedDB), syncs when online
9. **Data isolation**: All data scoped by `license_id`, enforced by RLS
10. **Currency**: IDR (integer, no decimals)
11. **Language**: UI in Bahasa Indonesia
12. **App catalog**: Always fetched from `ksp_apps` table — never hardcode app count or app list

## 12. Important Design Decisions

When working on this codebase, respect these decisions:

1. **Server Components by default** — only use `"use client"` when interactivity is needed
2. **Server Actions for mutations** — no API routes unless necessary
3. **All UI text in Bahasa Indonesia** — this is an Indonesian product
4. **Mobile-first design** — POS apps used primarily on tablets and phones
5. **Supabase client from packages/db** — never create Supabase clients directly in apps
6. **shadcn/ui components from packages/ui** — import from `@kasirsolo/ui`
7. **WhatsApp + PIN auth for kasir apps** — do NOT use Supabase Auth for kasir app users
8. **Admin auth via Supabase Auth** — email + password, the only place Supabase Auth is used for login
9. **Dynamic app catalog** — always fetch from `ksp_apps`, never hardcode app list or count
10. **Constants as fallback only** — `constants.ts` KSP_APPS is a fallback, not the primary source
11. **license_id everywhere** — every app data query must be scoped by license_id

## 13. Common Tasks

### Adding a new page to a kasir app
1. Create route in `apps/kasir-{app}/src/app/{route}/page.tsx`
2. Use Server Component for data fetching
3. Import UI from `@kasirsolo/ui`
4. Auth check: verify session from IndexedDB (WhatsApp + PIN session, not Supabase Auth)
5. Data queries must include `license_id` filter

### Adding a new shared component
1. Create in `packages/ui/src/components/`
2. Export from `packages/ui/src/index.ts`
3. Follow shadcn/ui patterns

### Adding a new database table
1. Create migration in `packages/db/supabase/migrations/`
2. Include `license_id` column if it's app data
3. Add RLS policies
4. Regenerate types: `pnpm db:generate-types`
5. Add query functions in `packages/db/src/queries/`

### Adding a new kasir app
1. Create app in `apps/kasir-{name}/`
2. Add record to `ksp_apps` table (via admin or migration)
3. Create app-specific DB tables with `{abbrev}_` prefix
4. Implement WhatsApp + PIN login page
5. Do NOT hardcode the new app in landing page — it will appear automatically from `ksp_apps`
